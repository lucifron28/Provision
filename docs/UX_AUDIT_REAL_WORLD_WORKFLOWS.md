## Confirmed findings

| Priority | Workflow | Observed behavior | User impact | Acceptance condition |
| --- | --- | --- | --- | --- |
| P1 | Add inventory | The advanced form requires a storage location even though the API accepts one as optional. Product creation and batch creation are separate requests, so a lost response between them can leave a product without stock. A new product also defaults silently to `pcs`, even when the unit is unknown. | Routine groceries take more work, and retrying a partial add can create confusing state. | Add a familiar item with identity, an explicitly selected unit, and quantity; keep detailed fields available; commit new product and initial stock atomically; exact retries do not duplicate either record. |
| P1 | Maintain stock | Product detail accepted a quantity and the backend consumed FEFO batches, but consume requests had no durable client retry record. Disposal was batch-wide, while quantity correction was separate. Unsupported legacy units also allowed decimal entry in some forms despite the backend treating unknown units conservatively as counts. | A timed-out consume could be repeated, partial disposal required manual correction, and invalid fractional edits failed only after submission. | Implemented on this branch: exact decimal requests are idempotent, saved in device-only Keychain before send, and retried unchanged after an unknown result. Partial discard and stock correction create separate ledger events; stale batch writes are rejected. The UI permits whole-number consume, discard, and adjustment for unknown units and asks users to correct the unit before adding stock or using fractions. New UI coverage includes the 58-scenario full gallery. macOS execution remains pending. |
| P1 | Shopping to pantry | Shopping items store `is_bought`; the bought filter shows them as “Purchased.” Clearing completed items deletes those rows. There is no review step that records actual quantities as pantry stock. | Purchased amounts can diverge from planned amounts, and clearing loses the path to stock intake. | Implemented locally: purchased rows remain pending until reviewed; the server validates household ownership, timestamp, unit, and product; exact retries replay a saved response; add/exclude decisions commit atomically. UI and screenshot coverage are added but await macOS CI. |
| P2 | Recipe substitutions | Recipe detail stores server-evaluated selections and renders them, but the shopping preview request contains no substitutions. The preview explicitly says it uses stored recipe ingredients. | Shopping quantities can describe the original ingredient after the user chose a substitute. | Implemented on this branch. Backend tests pass for replacement safety and quantity recalculation and rejection of unlisted replacements. UI verification is queued with the branch check. |
| P2 | Expiring food | Home offered a one-unit “Consume” action for an expiring item; the product detail screen has a quantity entry flow. | The shortcut could not record partial measured use or a multi-unit use. | Implemented on this branch: Home asks for the actual amount, enforces count-unit bounds, and uses the same persisted idempotent request recovery as product detail. Server stock remains authoritative. UI verification is pending. |
| P3 | Trust and accessibility | Pip Chat has separate chat and allergy-sharing consent; preferences explain that missing allergy declarations are not treated as allergy-free. Label review is a separate guided flow. Gallery coverage exercises large text and safety states. | These are useful foundations; remaining work should focus on clarity and real-device behavior rather than replacing them. | Preserve server consent and safety decisions; test VoiceOver, large text, keyboard, camera, and barcode behavior on real hardware before claiming those checks. |
